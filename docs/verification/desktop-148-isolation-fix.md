## 问题与改动

旧 preview9 的代理会话给共享安装内核增加会话 package SID 权限，在本机引起另一普通 148 环境的 GPU 加载拒绝访问；同一精确内核副本的授权/撤销真实对照见[历史记录](desktop-148-repair.md)。这些失败不删除、不追认通过。

Ant-Browser `61feab721f71d65301dfa45397cb9e15e28e8fd8` 的[正常启动链](https://github.com/black-ant/Ant-Browser/blob/61feab721f71d65301dfa45397cb9e15e28e8fd8/backend/app_instance_start_execute.go)通过独立数据目录直接启动内核，没有本项目额外的共享内核 package ACL 操作。用户明确要求采用这一共享内核方案，不再增加外层系统隔离。参考的是结构和行为，没有复制第三方代码。

本次保持原安装记录、精确 148 构建、seed、用户数据目录及代理绑定。直连与代理环境均使用原安装内核；新代理会话不创建 AppContainer、不改内核/profile/窗口站 ACL、不创建内核副本。仍保留本机认证桥、准确 Job 进程树和浏览器原沙箱，前检失败阻止启动，桥故障停止对应会话，原环境按原 ID 重试。旧日志中的容器和权限资源继续按既有归属清理，不直接丢弃。

此前提出过每会话复制 76 个内核文件、约 425 MiB 的方案；用户质疑成本后暂停，并明确改为上述共享方式。该方案没有构建或交付，不作为最终实现。不会增加每环境内核副本，也不增加实例数量配额。

当前代理边界是浏览器显式代理配置及应用故障处理，不再宣称操作系统强制隔离所有出网路径或管理器崩溃期间全路径零泄漏。此前 D017/AppContainer 验证留作历史，不能挪用为新方案的证据。
